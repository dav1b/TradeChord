# Vercel deployment and performance plan

Last updated: 2026-07-27

Production deployment is an architectural requirement for TradeChord. The
target is a globally available, fast, responsive public application—not a
local analytical tool that is merely uploaded at the end.

## 1. Production model

The preferred production shape is:

```text
Git repository
  → Vercel preview or production build
  → prerendered SvelteKit application shell
  → immutable JavaScript/CSS and versioned JSON on Vercel's CDN
  → local browser interaction and scene transitions
```

The production request path must not include:

- Python;
- WITS;
- data regeneration;
- canonical CSV parsing;
- a database;
- per-interaction server computation.

The Python pipeline runs before deployment and commits validated browser
projections. Vercel builds only `web/`.

## 2. Vercel project configuration

Configure one Vercel project with:

- repository: the TradeChord monorepo;
- Root Directory: `web`;
- framework: SvelteKit;
- install command: `npm ci`;
- build command: `npm run build`;
- Node version: the version declared by `.nvmrc` and `package.json`;
- production branch: the repository's chosen main branch;
- preview deployments enabled for pull requests;
- skipped deployments for commits that do not affect `web/` or its deployment
  configuration.

The project root setting means Vercel cannot read files outside `web/`.
Therefore every runtime artifact must remain under `web/static/` or be
generated by the web build. The pipeline itself must not be copied into the
deployment.

Keep `@sveltejs/adapter-vercel`. Do not introduce `vercel.json` rewrites around
SvelteKit routes unless a concrete routing need cannot be expressed through
SvelteKit.

## 3. Static-first rendering

TradeChord's published data is immutable and the main experience is the same
for every visitor. Prefer prerendered routes and static assets over runtime
server functions.

Recommended route design:

- prerender `/` and `/all`;
- make the reporter the meaningful path segment, for example `/country/DEU`;
- keep year, flow, partner, product, and representation in query parameters
  unless a later URL design proves they belong in the path;
- enumerate the finite reporter routes from the committed country index at
  build time;
- let client-side navigation transform the existing scene without a hard
  document navigation.

This produces shareable URLs while keeping the route set finite and
prerenderable. If a future route genuinely needs request-time behavior, isolate
that route instead of converting the entire application to runtime SSR.

Before changing rendering mode, verify:

- direct URL entry;
- refresh of a detailed analytical URL;
- preview deployments;
- `404` behavior;
- browser back/forward;
- disabled JavaScript fallback expectations;
- crawler-visible title, description, and basic scene summary.

## 4. CDN and browser caching

Use the immutability already present in dataset versions.

### Versioned artifacts

These paths are immutable:

```text
/data/2026-07.1/overview.json
/data/2026-07.1/countries/DEU.json
/data/<version>/...
```

They should receive a long-lived public cache policy:

```text
Cache-Control: public, max-age=31536000, immutable
```

Never modify the bytes at an already published versioned URL.

### Active pointer

`/data/current.json` is mutable between deployments. It must not receive the
same year-long browser cache policy. Use revalidation or a short browser TTL so
a newly deployed application resolves the new active release.

The active pointer already includes the manifest hash. Continue updating it
last during release publication.

### Build assets

Vite content-hashes JavaScript and CSS. Those hashed assets should remain
immutable and CDN-cacheable. Do not add query-string cache busting or stable
handwritten filenames for compiled bundles.

Verify actual production response headers with `curl` after deployment; do not
assume local Vite behavior matches the CDN.

## 5. Data-loading architecture

The continuous-scene frontend should not download every possible analytical
detail on initial load.

Use progressive, interaction-shaped resources:

```text
/data/<version>/countries/DEU/core.json
/data/<version>/countries/DEU/years/2022.json
/data/<version>/countries/DEU/partners/CHN.json
/data/<version>/countries/DEU/comparisons/2019-2022.json
```

The exact split must be chosen through measurement, but the principles are:

1. Initial data renders the first useful scene.
2. The current-year scene supports the first partner selection immediately.
3. Likely next-state data is prefetched after the initial scene becomes
   interactive.
4. Partner history is loaded only when the user narrows to that relationship,
   unless the measured country payload is already sufficiently small.
5. Fetches are cancellable or safely ignored when selection changes.
6. The same URL is never used for different immutable content.
7. A failed detail fetch leaves the current scene usable and offers retry.
8. Loading indicators belong to the affected entity or scene, not always to a
   full-page overlay.

The current release is approximately 7.6 MB across all country projections,
while individual country files are roughly 250–280 KB uncompressed. Users only
need one country at a time, so the existing per-country boundary is sound. The
future risk is allowing hierarchical products, mirror flows, detailed
partners, and comparison artifacts to accumulate in a single country file.

## 6. Browser computation

Transitions must not depend on a server round trip, but that does not mean all
work belongs on the main thread.

- Precompute trade totals, shares, balances, ranks, availability, and
  reconciled contribution values in the pipeline.
- Compute responsive geometry in pure D3 functions in the browser.
- Do not parse the canonical CSV in production.
- Avoid repeatedly constructing the full scene graph during pointer movement.
- Throttle year scrubbing to animation frames and discard superseded work.
- Cache geometry inputs by dataset version, scene, year, and viewport class
  where measurement shows a benefit.
- Use Web Workers only if profiling shows a calculation produces long tasks;
  do not add worker complexity preemptively.
- Prefer SVG initially. Introduce Canvas only after real entity counts and
  devices demonstrate an SVG rendering bottleneck.

## 7. JavaScript and dependency policy

The future scene should not become one monolithic route bundle.

- Import D3 submodules rather than adding new umbrella visualization
  libraries.
- Lazy-load map, waterfall, mirror-quality, and other advanced
  representations until requested.
- Keep the initial country scene and state controller in the primary bundle.
- Avoid shipping Python-derived schemas, release tooling, or canonical parsing
  code to the browser.
- Inspect Vite chunk output on every major frontend milestone.
- Add a bundle-size check after measuring and agreeing the baseline.
- Treat new dependencies as performance decisions: record shipped size,
  execution cost, maintenance state, and whether native/Svelte/D3 primitives
  already cover the need.

## 8. Performance budgets

Establish a measured baseline on a deployed preview, then enforce budgets in
CI. Initial targets:

| Measure | Initial target |
|---|---:|
| Largest Contentful Paint, mobile P75 | ≤ 2.5 s |
| Interaction to Next Paint, P75 | ≤ 200 ms |
| Cumulative Layout Shift, P75 | ≤ 0.1 |
| Initial app JS, compressed | ≤ 200 KB |
| Initial country data, compressed | ≤ 100 KB |
| One next-scene detail payload, compressed | ≤ 150 KB |
| Main-thread long task | No routine task over 50 ms |
| Animation work | Target one frame within 16.7 ms |

These are initial engineering budgets, not claims about current production
measurements. Adjust them only from measured preview/production evidence and
record the reason.

Test at least:

- a mid-range mobile viewport with CPU and network throttling;
- desktop;
- a large country projection;
- a rapid year scrub;
- repeated forward/back scene transitions;
- cold cache and warm cache;
- reduced-motion mode.

### First production baseline — 2026-07-27

Measured against `https://trade-chord.vercel.app` after the first
Network ↔ Rank deployment:

| Resource | Compressed transfer | Observed TTFB | Result |
|---|---:|---:|---|
| `/` | 57,174 B | 0.311 s | Within initial transfer budget |
| `/all` | 20,902 B | 0.345 s | Within initial transfer budget |
| USA country projection | 35,360 B | 0.115 s | Within initial data budget |

The production Playwright journey passed country navigation, representation
switching, partner selection and re-ranking, browser history, direct scene URL
restoration, cross-filtering, and `/all`, with no captured console errors.

Header verification found:

- public routes and data return `200`;
- `current.json` identifies schema 2 and release `2026-07.1`;
- Vercel edge caching is active for data resources;
- versioned projection responses still advertise
  `Cache-Control: public, max-age=0, must-revalidate`.

The versioned projection header does not yet meet the intended immutable-cache
policy. Adding and verifying a one-year immutable browser policy for
`/data/<version>/...` is the next deployment-hardening task. `current.json`
must remain separately revalidated.

## 9. Build and deployment gates

The Vercel build should stay deterministic and network-independent apart from
package installation:

```text
npm ci
  → svelte-check
  → vite build
  → browser smoke tests against built output
  → deployment
```

WITS collection must never occur in the Vercel build.

Add these gates incrementally:

- schema and active-release integrity verification before deployment;
- missing referenced projection detection;
- bundle-size report and agreed size limits;
- compressed data-payload report;
- direct-entry tests for shareable analytical URLs;
- response-header checks against a preview deployment;
- Lighthouse or equivalent lab checks for regression detection;
- accessibility checks for the primary scene journey.

Preview deployments are the review environment for interaction and motion.
Production promotion should occur only after the preview uses the intended
active data release and passes smoke checks.

## 10. Runtime reliability

- Enable Vercel skew protection if long-lived sessions show deployment-version
  conflicts. The visual explorer contains meaningful client state, so an
  avoidable hard reload is particularly disruptive.
- Treat unsupported schema versions as an explicit error with recovery
  guidance.
- Keep the previous immutable data release deployable for rollback.
- Ensure a missing optional detail resource does not destroy the base country
  scene.
- Log or measure projection fetch failures without collecting sensitive
  analytical selections unnecessarily.
- Add a user-visible build/release identifier to error diagnostics.

## 11. Measurement and observability

After the first deployment:

1. Enable Vercel Speed Insights.
2. Measure P75 LCP, INP, and CLS by route and device.
3. Establish whether the country scene, `/all`, or a particular transition is
   the main bottleneck.
4. Compare preview and production after major changes.
5. Add Web Analytics only if route and feature usage will inform product
   decisions.
6. Decide the appropriate Speed Insights sampling rate from traffic and plan
   limits.

Real-user measurements should guide optimization. Lighthouse and Playwright
remain useful gates, but they do not replace field performance.

## 12. Deployment sequence

### Phase 1: first public baseline

1. Commit and push the current refactor.
2. Create the Vercel project with `web` as its root.
3. deploy a preview from the refactor branch.
4. Verify routes, data files, response headers, errors, and direct links.
5. Capture bundle, payload, Lighthouse, and browser performance baselines.
6. Enable Speed Insights after reviewing privacy and usage settings.

### Phase 2: static and cache hardening

1. Prerender the finite public route set.
2. Add and verify differentiated cache headers for versioned data and
   `current.json`.
3. Add direct-entry and refresh tests.
4. Add payload and bundle reports to CI.

### Phase 3: continuous-scene prototype

1. Develop against preview deployments as well as localhost.
2. Implement the first chord-to-ranked or chord-to-bilateral transformation.
3. Profile INP, long tasks, layout stability, and animation frames.
4. Split or prefetch detail projections only when measurements justify it.

### Phase 4: progressive advanced scenes

Add product hierarchy, history, waterfall, geography, ROW expansion, and
mirror comparison as lazy representations backed by independently versioned
data capabilities.

## 13. Non-goals

- Do not move WITS collection into Vercel Functions.
- Do not add a production database merely to serve immutable historical data.
- Do not introduce runtime SSR for every route without a demonstrated need.
- Do not solve payload growth by making the browser download the canonical
  matrix.
- Do not optimize animations from localhost alone.
- Do not depend on a deployment-specific rewrite that breaks SvelteKit's
  understanding of the URL.
